First read the capabilities skill's `references/host-adapter.md` and resolve the plugin root for this host. Below, `factory` means `python3 "${FACTORY_PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/factory/factory.py" --repo .`. Item paths like `items/<id>/...` live under `.factory/` — the full path is `.factory/items/<id>/...`.

Run this skill in a fresh context using the capabilities skill's `references/host-adapter.md`; nothing from the invoking session may be treated as input. The item id arrives as the skill argument; everything else is read from disk — `factory status --json`, `.factory/items/<id>/...`, and the brain surfaces this skill names below. Your final message is the report the dispatcher acts on: state the outcome (the stage advanced to, or the failure/pause reason, verbatim where a gate refused), name the key artifact paths written, and keep it to a few lines — never paste file contents into it.

For Workflow-based fan-out of parallel plan tasks, see the capabilities skill's `references/workflow-fanout.md` (degraded path — parallel subagents — is the default).

## Contract

- **Entry stage:** `implement`. The gate into `implement` already required `plan.md` with at least one `- [ ]` task.
- **Artifacts produced:** branch `factory/<item-id>`, checkboxes ticked in `plan.md` as tasks land, the implementation commits themselves.
- **Exit — success:** with feasibility disabled, `factory log ITEM implement.completed --data '{"tasks": N, "tests": "<summary>"}'` then `factory advance ITEM review`. With feasibility enabled, the final `factory plan-finalize` emits completion atomically; do not log it separately. The `review` gate checks the exact branch ref and completion event in either mode.
- **Exit — task failure:** leave the branch intact (never delete work), `factory log ITEM implement.failed --data '{"task": "<name>", "attempts": 2}'`, and report the failure to the dispatcher. Do not call `advance` — the dispatcher owns the blocked transition after repeated failures.

## Rework entry

With feasibility disabled, retain the existing rework behavior: when prior `review.rejected` events exist and the plan is complete, read the authoritative blocking findings in `reviews/synthesis.md`, append one task per blocking finding, and run them through the normal task loop on the existing branch.

With feasibility enabled, read the capabilities skill's `references/plan-feasibility.md`. Never invent or append rework here. The rejecting review, verify, or assure stage must already have installed source-linked plan and acceptance replacements through `factory plan-rework`. An interrupted implementation simply resumes its existing unchecked task without adding tasks. A completed plan is a refusal, not a signal to synthesize work.

## Steps

1. **Isolated branch.** Use `superpowers:using-git-worktrees` to get an isolated workspace when its native-tool path is available; otherwise create a plain branch. Either way the branch must be named exactly `factory/<item-id>`, cut from the repo's default branch — `using-git-worktrees`' `git worktree add -b` (or a plain `git branch` + checkout) creates this ref in the shared `.git`, which is what the `review` gate inspects. Don't rename or prefix it differently.
2. Read `items/<id>/plan.md` once to establish the task list; do not re-derive it from the spec. In enabled mode, later worker input comes only from each durable dispatch handoff.
3. **Headless path (capabilities skill — "Headless worker" row):** if that capability is present, execute this item's plan out-of-process by running `factory work <item-id>` instead of the in-process dispatch below. It owns enabled dispatch, result binding, scope inspection, guarded marker finalization, completion, and measured spend. Treat exit 2 safety reasons from `references/plan-feasibility.md` as terminal for the attempt: retain the branch/result, never auto-retry, and never claim completion. Otherwise, fall through to the in-process path: before each in-process implementer dispatch acquire an outer claim with `factory ownership acquire ITEM --worktree <checkout> --json`; retain the returned acquisition JSON field `inherited` in the orchestrating session, and keep its `owner_token` there as `FACTORY_IMPLEMENTATION_OWNER`. Pass the token only as env to Factory nested ownership checks; never put it in prompt, plan, log, commit, review receipt, artifact, task evidence, or handoff. Within the held window, execute each task via `superpowers:subagent-driven-development`: use one fresh implementer subagent per task with `agents/implementer.md`, followed by a fresh independent reviewer using `agents/reviewer.md`. Follow the capabilities skill's fan-out guidance for concurrency-safe supporting work while preserving that per-task implementer/reviewer sequence. Hold the claim through the implementer, fresh independent reviewer, checkout cleanup, marker finalization, and task-evidence finalization. Call `factory ownership check ITEM --worktree <checkout>` at every one of those five boundaries. In enabled mode, immediately before the initial implementer dispatch for each selected task run `factory plan-dispatch ITEM --task 1 --json`; give the subagent only its immutable `handoff` wrapped in explicit implement/TDD/test/commit/owned-path instructions. Retain that original ticket and handoff through the task's reviewer and its one allowed fix dispatch; never issue a replacement fix ticket, because final scope inspection must remain cumulative from the original baseline. After clean review, run the task's tests. If this ticket would finalize the last unchecked marker, determine that from the captured handoff and run the full item/project suite before writing success evidence. Then write a schema-valid successful `items/<id>/worker/result.json` bound to the original `ticket_id` and run `factory plan-finalize ITEM --ticket TICKET_ID --json`. In disabled mode, use the existing plan task text directly. Only an invocation whose acquire returned `inherited: false` owns the outer release and calls `factory ownership release ITEM --worktree <checkout>` after success or handled-failure evidence is final; an invocation whose acquire returned `inherited: true` must never release the inherited claim. Refusal stops the contender before dispatch; release failure is fail-closed and stops without asserting release. Production nested work inherits with the same env token. Neither prose, log events, nor process mutex is authority.
4. As each task's review and required tests come back clean, enabled mode uses `plan-finalize` to tick exactly the captured marker atomically; the final marker is never finalized before the full suite is green. Disabled mode retains the direct `- [ ]` to `- [x]` edit committed alongside (or immediately after) the task's commits.
5. **On a task failing twice** (implementer + fix dispatch still can't clear task review after a second attempt): stop working this item. Leave the branch as-is — do not discard partial progress — log `implement.failed` per the Contract, and report to the dispatcher, which will apply its own two-strikes-then-blocked rule.
6. When every task is ticked, disabled mode runs the item's full suite and only on green logs `implement.completed`. Enabled mode confirms the full suite passed before the final `plan-finalize` and that the finalizer emitted completion. Then advance to `review` per the Contract.

## Spend logging

At every subagent fan-out point for this item — in step 3, when each per-task implementer or reviewer dispatch (or batch) completes, and equally for the rework-path dispatches under Rework entry — the orchestrating session logs one spend event: `factory log ITEM spend --data '{"provenance":"measured","stage":"implement","source":"factory-implement","dispatches":<n>,"tokens":{"total":<n>}}'` (include `"input"`/`"output"` instead or additionally when the harness reports them) using the token counts the harness reports for those subagents. If the harness surfaces no token usage, log the same event with `"provenance":"proxy"` and **no** `tokens` key. Never estimate or invent token numbers; the orchestrator's own main-loop burn is never logged as measured. The engine neither requires nor verifies these events at gates — this is convention, not a gate.

## Notes

- Never advance past a red suite — a false `implement.completed` would let a broken branch reach `review` looking finished.
- The branch is never deleted here even on success; `ship` is the only stage that removes it (and only under the `auto` merge policy).
